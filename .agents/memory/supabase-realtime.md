name: Supabase realtime sync
description: How cross-device admin lifecycle sync works and its Supabase-side requirement
---
Admin views subscribe to postgres_changes on `user_profiles` via @supabase/supabase-js (already a react-app dependency). Row events are debounced (~250ms) into one `syncLifecycleFromDb()` refresh. The old 10s poll and visibility refresh remain but only fire while the channel is NOT `SUBSCRIBED`; on reconnect a catch-up sync runs.
**Why:** instant cross-device convergence with polling kept solely as a fallback.
**How to apply:** if realtime updates don't arrive, check that the table is in the `supabase_realtime` publication on the external Supabase project — without it the channel subscribes but delivers nothing, and the poll fallback silently masks the gap only when the socket is down. `user_profiles` was added (user ran the ALTER PUBLICATION SQL, verified July 2026). Admin views also subscribe to `organizations`, `packages`, and `client_documents` (same channel, per-table 250ms debounce into refreshOrgs/refreshPackages/refreshAdminDocs); as of Aug 10 2026 those three tables AND `admin_settings` ARE in the publication (user ran ALTER PUBLICATION for admin_settings on Aug 10 2026; all four verified by a live headless test: `pnpm --filter @workspace/api-server run test:realtime`, which subscribes, no-op PATCHes a row per table with the service key, and asserts the event within ~3s — a no-op PATCH still emits an UPDATE event). Note `admin_settings` has NO `id` column — it's keyed by (key, company_id); PATCH filters must use those. Idempotent runbook: database-updates/2026-08-10-realtime-publish-admin-settings.sql. Note: the anon key cannot run DDL and no admin credentials exist in this workspace — publication changes must be run by the user in their Supabase dashboard. To verify delivery headlessly: subscribe with supabase-js in Node, PATCH a row via REST, expect the event within ~1-3s.
Team Hub chat uses a **broadcast** channel (typing hints + "new-message" nudges that trigger an immediate reload) instead of postgres_changes — broadcast needs NO table publication, so it's the right tool when the user can't/hasn't run ALTER PUBLICATION. Unread state is client-side: per-user last-viewed timestamps in localStorage (`teamhub_seen_<uuid>`), with a `teamhub-seen` window event so the app shell's tab badge (polling hook in the shared teamUnread lib) updates instantly. The 8s poll remains the delivery fallback.
The same pattern also covers the live-huddle banner (`huddle_rooms`) and notification bell (`notifications`). Key lesson: a channel can report SUBSCRIBED even when a table is NOT in the publication and deliver nothing — so never suppress the fallback poll on SUBSCRIBED alone; only suppress it after a real row event has recently arrived. **Status (July 31 2026):** `notifications` was already in the publication; `huddle_rooms` was added via idempotent DO block (confirmed by successful no-error execution). Both tables are now in `supabase_realtime`. Instant delivery is active for the huddle banner and notification bell.
